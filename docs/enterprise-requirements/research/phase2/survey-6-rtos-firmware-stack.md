## Survey 6: RTOS + secure firmware stack

_Phase-2 research item 6 — hardens Appendix B.3's sketch (Zephyr/FreeRTOS + mbedTLS/wolfSSL + MCUboot + littlefs + discrete-TPM-or-on-die root) into concrete requirements-feed material for the ENT-NET/ENT-AIR PolarFire Hub. Scope: no-Linux RTOS control plane, secure boot chain, TLS/crypto library + FIPS posture, northbound protocol stack realism, signed-OTA/SBOM tooling, and an engineering-effort reality check._

### Recommended stack

**RTOS: Zephyr, not FreeRTOS, as the primary recommendation.**

PolarFire SoC's Icicle Kit (the dev-kit stand-in for the eventual production part) has a **`mpfs_icicle` board target that is in-tree and "Maintained" in mainline Zephyr** — official docs live on `docs.zephyrproject.org`, not a fork [Zephyr mpfs_icicle board docs](https://docs.zephyrproject.org/latest/boards/microchip/mpfs_icicle/doc/index.html). It supports both the E51 monitor hart and the U54 application harts, including an SMP-capable multi-U54 build variant, with GPIO/I2C/SPI-QSPI/UART/RTC/SPI-NOR-flash/CLINT/PLIC drivers already wired [Zephyr mpfs_icicle docs](https://docs.zephyrproject.org/latest/boards/microchip/mpfs_icicle/doc/index.html). Microchip also maintains a dedicated sample/demo repo for it [polarfire-soc-zephyr-applications](https://github.com/polarfire-soc/polarfire-soc-zephyr-applications). Critically, Zephyr already carries **in-tree the specific subsystems this survey's requirements need**: a native HTTP/HTTPS server (`CONFIG_HTTP_SERVER`, HTTP/1.1 and HTTP/2, TLS sockets) that superseded the now-"obsolete" CivetWeb integration [Zephyr HTTP server docs](https://docs.zephyrproject.org/latest/samples/net/sockets/http_server/README.html) [civetweb repo marked obsolete](https://github.com/zephyrproject-rtos/civetweb); a native UDP syslog backend emitting RFC 5424 [Zephyr syslog_net sample](https://docs.zephyrproject.org/latest/samples/net/syslog_net/README.html); a native `west spdx` SBOM generator [Zephyr west extension commands](https://docs.zephyrproject.org/latest/develop/west/zephyr-cmds.html); and first-class MCUboot integration via sysbuild (`SB_CONFIG_BOOTLOADER_MCUBOOT`) [MCUboot Zephyr integration — DeepWiki](https://deepwiki.com/zephyrproject-rtos/zephyr/9.1-mcuboot-bootloader-integration).

FreeRTOS is also a real, Microchip-documented option — it has been ported to the Icicle Kit, and Microchip explicitly demonstrates an AMP pattern running **FreeRTOS on one hart cluster and minimalist Linux on another** [PolarFire SoC bare-metal library docs](https://github.com/polarfire-soc/polarfire-soc-bare-metal-examples), reinforced by an IEEE reliability study that exercised bare-metal and FreeRTOS configurations on the part under proton irradiation [IEEE 10819376](https://ieeexplore.ieee.org/document/10819376/). But FreeRTOS is a bare scheduler kernel: it does not bundle a network stack, HTTP server, SBOM tooling, or MCUboot build-system glue, so every one of REQ-HUB-NET-020/021's protocol asks would be assembled from third-party pieces rather than configured from in-tree subsystems. **Recommend Zephyr as primary; do not use the FreeRTOS+Linux AMP pattern** even though Microchip documents it — running any Linux instance on the Hub, even on a spare hart, reintroduces exactly the networked attack surface REQ-HUB-COMMON-002 and Appendix B.3 are written to avoid. (Aside, not evaluated further: NuttX has an independent RISC-V International-documented PolarFire SoC port [RISC-V International — NuttX on PolarFire SoC](https://riscv.org/blog/porting-nuttx-real-time-operating-system-on-polarfire-soc-fpga/); ecosystem-breadth footnote only, outside Appendix B.3's named pair.)

**Boot chain: HSS is the platform root; MCUboot/wolfBoot is a second, separate layer needed on top of it — these are not the same problem.**

PolarFire SoC's real chain is: System Controller (PUF-rooted, factory silicon) → Boot Mode 2/3 secure boot → **Hart Software Services (HSS)**, the zero-stage bootloader/system monitor stored in eNVM [PolarFire SoC HSS — DeepWiki](https://deepwiki.com/polarfire-soc/polarfire-soc-documentation/2.1-hart-software-services-(hss)). Verified against Microchip's own authentication doc, this chain runs on **three distinct key pairs**: User Code Signing Keys (UCSK/UCSQ) sign the Secure Boot Image Certificate that authenticates eNVM content at the factory stage; HSS Payload Signing Keys (HPSK/HPSQ) sign the HSS payload itself (typically U-Boot, but HSS "supports signing generic payloads"); and a separate FIT-image key signs the Linux/kernel/initramfs bundle when Linux is the payload — ECDSA NIST P-384 for the first two, SHA-256/RSA-4096 for the FIT image [polarfire-soc-documentation linux-boot-authentication.md](https://github.com/polarfire-soc/polarfire-soc-documentation/blob/master/how-to/linux-boot-authentication.md). Anti-rollback exists at this layer as a **certificate-version-vs-revocation-threshold check** with an atomic update guarantee (a failed threshold update is guaranteed to leave either the old or new value, never a corrupt one) [UG0881 booting/configuration guide](https://ww1.microchip.com/downloads/aemdocuments/documents/fpga/ProductDocuments/UserGuides/microsemi_polarfire_soc_fpga_booting_and_configuration_user_guide_ug0881_eap2_v2.pdf) — functionally an anti-rollback mechanism, though the sources do not confirm it is implemented as a dedicated hardware monotonic counter distinct from an NVM-stored threshold value [unverified — mechanism detail].

The documented worked examples for this chain are **Linux/U-Boot-payload-centric**; the docs state HSS "supports signing generic payloads" but do not walk through a bare-RTOS-ELF payload end to end [polarfire-soc-documentation linux-boot-authentication.md](https://github.com/polarfire-soc/polarfire-soc-documentation/blob/master/how-to/linux-boot-authentication.md). Separately, **Microchip's own field-update mechanism (Auto Update / In-Application Programming, AC466) reflashes the whole eNVM image** and is explicitly *not* power-loss-atomic at that granularity: "if there is a power interruption while Auto Update or IAP is updating the eNVM... the partially programmed eNVM... causes the user design to malfunction" [AC466 Auto Update / IAP application note](https://ww1.microchip.com/downloads/aemDocuments/documents/FPGA/ApplicationNotes/ApplicationNotes/microsemi_polarfire_fpga_auto_update_and_in_application_programming_application_note_ac466_v7.pdf). That is precisely the failure mode an A/B-slot swap-and-revert bootloader exists to eliminate for the RTOS application image — so the realistic architecture is **two tiers**: (1) HSS/System-Controller-level authentication for rare, high-ceremony bitstream/eNVM reflashes, and (2) MCUboot- or wolfBoot-managed A/B slots *inside* the payload HSS boots, for routine RTOS firmware OTA with real rollback safety. Recommend not relying on HSS's native Auto-Update/IAP path alone for the RTOS-image update case in REQ-HUB-NET-012/AIR-013.

Between MCUboot and wolfBoot for that second tier: **MCUboot's Zephyr integration is broad and proven in general** (sysbuild-native, works across many Zephyr-supported boards and, per its docs, RISC-V is one of its architecture targets in principle) [MCUboot design docs](https://docs.mcuboot.com/design.html), but **no public evidence was found of anyone chaining MCUboot specifically underneath HSS on PolarFire SoC** — searches on this exact combination returned only that "PolarFire SoC primarily uses HSS as its bootloader" with no MCUboot integration writeups [unverified — absence of evidence, not evidence of absence]. **wolfBoot is a real alternative worth weighing**: it is explicitly OS-agnostic (RTOS/Linux/bare-metal), has shipped RISC-V support (reference target: SiFive HiFive1 FE310, a small RV32IMAC part — not PolarFire's RV64GC application harts, so still a port) [wolfBoot adds RISC-V support](https://www.wolfssl.com/wolfboot-adds-risc-v-support/), and wolfSSL has done recent work integrating wolfBoot with Zephyr specifically for CRA compliance [wolfBoot/wolfPSA Zephyr CRA integration](https://www.wolfssl.com/replacing-tf-m-on-armv8-m-wolfboot-secure-domain-wolfpsa-now-integrated-with-zephyr-for-cra-compliance/). Pairing wolfBoot with wolfCrypt/wolfSSL (below) gives a single-vendor, portable-C security stack rather than gluing MCUboot (ARM/Zephyr-sysbuild-flavored) onto Microchip's own HSS flow. **Neither path is proven on PolarFire specifically — both are porting work; wolfBoot looks like the lower-integration-risk option given vendor coherence with the crypto layer, but this needs a bring-up spike before it's load-bearing.**

**TLS/crypto: wolfSSL/wolfCrypt for the FIPS-bearing path; mbedTLS stays relevant as Zephyr's free in-tree default.**

wolfCrypt holds **two live FIPS 140-3 certificates**: #5041 (posted July 18, 2025) and the world's-first SP800-140Br1-compliant automated-pilot certificate #4718 (posted July 11, 2024, valid through July 10, 2029) [wolfCrypt FIPS 140-3 cert #5041](https://www.wolfssl.com/wolfcrypt-fips-140-3-certificate-5041-now-validated/) [wolfSSL SP800-140Br1 announcement](https://www.wolfssl.com/wolfssl-secures-the-worlds-first-sp800-140br1-compliant-fips-140-3-validation-certificate/). Its validated operating-environment list spans FreeRTOS, OpenRTOS, VxWorks, QNX and several others — **but RISC-V does not currently appear on that list** [wolfCrypt FIPS 140-3 operating environments](https://www.wolfssl.com/wolfcrypt-fips-140-3-operating-environments/). Extending an existing FIPS validation to a new operating environment is a real CST-lab exercise, not paperwork, and rides the same CMVP queue discussed below. **mbedTLS/TF-PSA-Crypto has no FIPS 140-3 certification** — confirmed both by its own FAQ ("not FIPS certified") and by the absence of any mbedTLS entry when cross-checked against how CAVP/CMVP validation actually works [Is Mbed TLS FIPS certified?](https://mbed-tls.readthedocs.io/en/latest/kb/generic/is-mbedtls-fips-certified/); it is dual Apache-2.0/GPL-2.0-or-later, so it is free and already Zephyr's default PSA Crypto backend [Mbed TLS license](https://github.com/Mbed-TLS/mbedtls/blob/development/LICENSE) [Zephyr PSA Crypto service](https://docs.zephyrproject.org/latest/services/crypto/psa_crypto.html) — a legitimate no-FIPS/cost-down configuration, but it cannot satisfy a "FIPS 140-3-validated crypto" claim on its own.

**The Athena coprocessor is real and RTOS/bare-metal-reachable, but its certification does not equal "FIPS 140-3 validated."** The MSS-integrated Athena TeraFire EXP-F5200B supports the CNSA suite with DPA-resistant countermeasures, driven from bare-metal/RTOS code via Microchip's Cryptographic Applications Library (CAL) — bare-metal CAL examples exist in the current example repo [PolarFire SoC bare-metal examples](https://github.com/polarfire-soc/polarfire-soc-bare-metal-examples) [Using the PolarFire SoC Cryptographic Processor](https://www.controlpaths.com/2025/10/26/terafire-on-polarfire-soc/), and it carries **CAVP algorithm certificates** (AES #3950, SHA-1/2 #3258, HMAC #2573, DSA #1077, RSA #2018, ECDSA #867, DRBG #1153) [PolarFire FPGA/SoC Security User Guide](https://www.microchip.com/content/dam/mchp/documents/FPGA/ProductDocuments/UserGuides/Microchip_PolarFire_FPGA_and_PolarFire_SoC_FPGA_Security_User_Guide_VA%20(2).pdf). But **CAVP certifies individual algorithm correctness; FIPS 140-3 module validation is a separate, broader CMVP process** covering self-tests, key management, operational behavior and the module boundary — CAVP is a mandatory first step toward a module validation, not the validation itself [wolfSSL: CAVP vs CMVP](https://www.wolfssl.com/what-is-the-difference-between-cavp-and-cmvp/). No PolarFire/Athena-specific FIPS 140-2/140-3 **module** certificate turned up in this search [unverified — absence of evidence]. Practical read for REQ-HUB-COMMON-090: **the FIPS 140-3 module boundary should be wolfCrypt-FIPS running in software** (once/if extended to RISC-V), with Athena usable as an unvalidated performance accelerator alongside it — not marketed as itself being "FIPS validated." Also **no Zephyr-native PSA Crypto driver wraps CAL/Athena today**; NXP's own RW61x accelerator needed a purpose-built out-of-tree driver following the same PSA driver-interface pattern [NXP psa_crypto_driver](https://github.com/NXP/psa_crypto_driver) — a CEC-side Athena driver of similar shape is real, bounded porting work, not a drop-in.

### Signed-OTA + SBOM tooling norms

- **SBOM**: `west spdx --init` / `west build` / `west spdx` is a real, in-tree, mechanical pipeline producing **SPDX 2.3** documents (`app.spdx`, `zephyr.spdx`) covering application source, Zephyr source, build output, and module dependencies [Zephyr west extension commands](https://docs.zephyrproject.org/latest/develop/west/zephyr-cmds.html) [Practical SBOM Management with Zephyr and SPDX](https://www.zephyrproject.org/practical-sbom-management-with-zephyr-and-spdx-benjamin-cabe/). It has known rough edges — an open issue reports it listing modules present in the workspace but disabled/unused, i.e. over-inclusive rather than under-inclusive [Zephyr SPDX discussion #108287](https://github.com/zephyrproject-rtos/zephyr/discussions/108287) [Zephyr SPDX issue #82838](https://github.com/zephyrproject-rtos/zephyr/issues/82838). **CycloneDX is not natively produced** — SPDX is the native format; a CycloneDX deliverable (if a customer's tooling requires it specifically) needs a separate conversion step. Directly satisfies REQ-HUB-COMMON-014's "every release ships an SBOM," with the SPDX-vs-CycloneDX format choice flagged for Phase-3.
- **Anti-rollback at the application-image layer**: MCUboot's mechanism is a **security counter, independent of the semantic version number**, carried in a signed image TLV and compared against the currently active counter stored in a "non-volatile and trusted component" — enabled via `MCUBOOT_DOWNGRADE_PREVENTION`/`MCUBOOT_HW_ROLLBACK_PROT`, and for hardware-backed protection the target must implement the `security_cnt.h` interface itself [MCUboot design doc](https://github.com/mcu-tools/mcuboot/blob/main/docs/design.md). That interface has **no existing PolarFire implementation found** — it would need to be written against either a spare eNVM/OTP counter or (if reusable) the same NVM the HSS revocation threshold already lives in; sharing one physical counter across both layers vs. maintaining two is an open design choice worth resolving early, not discovering late.
- **OTA delivery mechanics** (staged rollout, health-check-triggered auto-rollback, offline signed-bundle equivalence) are layered above the bootloader and were already scoped by the prior customer-integration audit toward hawkBit DDI/Mender-class delivery with MCUboot-verified images [customer-integration-audit-2026-07-01.md §3.2] — this survey's contribution is confirming the bootloader/image-signing layer underneath that delivery mechanism is real but requires the HSS-chaining and security-counter porting work above; it is not a solved problem inherited for free from either Zephyr or MCUboot's general maturity.

Treat as a real but currently unscoped line item if SNMPv3 is not deferred.
- **FIPS 140-3 CMVP queue**: industry sources converge on **12–18 months from submission to active certificate**, with NIST reporting recent backlog-reduction progress [FIPS 140-3 transition effort — NIST CSRC](https://csrc.nist.gov/projects/fips-140-3-transition-effort) [Why the FIPS 140-3 transition is harder than it looks](https://www.encryptionconsulting.com/why-fips-140-3-transition-is-hard/). This is squarely relevant if any RISC-V OE-extension work for wolfCrypt FIPS is contemplated — start that conversation with wolfSSL early, not at Phase-4.
- **IEC 62443-4-1 SDL certification** (adjacent to this survey, owned by Phase-2 item 7 but relevant to effort sequencing): **6–12 months for a team with an already-mature secure development process, 18–24 months building from scratch** [IEC 62443-4-1 explained](https://cytal.co.uk/blog/iec-62443-4-1-explained-secure-development-lifecycle-requirements/).

### Engineering-effort realism note

What teams typically underestimate on this exact shape of project:

1. **The "system-integration tax," not any single component.** Each piece here (Zephyr's port, wolfSSL, MCUboot/wolfBoot, an HTTP server) is individually proven *somewhere*, but PolarFire is not a mainstream ARM Cortex-M target — the gluing-together is where schedule risk concentrates. General secure-boot literature backs this pattern bluntly: "implementing a secure bootloader from scratch for a specific project... may require as much development and testing as all the rest of the software components in the system" [Foundries.io on secure boot effort](https://www.foundries.io/insights/blog/secure-boot-embedded-devices/).
2. **The dual/heterogeneous boot-chain tax specific to FPGA SoCs.** This is not a generic MCU secure-boot problem — PolarFire authenticates a bitstream and a firmware payload through *separate* stages with *separate* key hierarchies (three key pairs, confirmed above), and FPGA-security literature calls this out as a general pattern: heterogeneous components with "different boot sequences, memory architectures, and security dependencies" that are genuinely harder to unify under one chain of trust than a single-core MCU [FPGA secure boot and PFR](https://promwad.com/news/fpga-security-secure-boot-pfr-embedded-systems). A team whose prior secure-boot experience is MCUboot-on-a-Cortex-M-MCU will under-scope this.
3. **FIPS 140-3 timeline as a critical-path item, not a late checkbox.** The 12–18-month CMVP queue [FIPS 140-3 transition effort](https://csrc.nist.gov/projects/fips-140-3-transition-effort), stacked against the September 21, 2026 FIPS 140-2 sunset [Three cryptographic deadlines](https://ciq.com/blog/three-cryptographic-deadlines-2026), means an OE-extension conversation with wolfSSL needs to start at or before Phase-3, not after a board exists.
4. **Key-custody ceremony, echoing the audit's own finding.** General secure-boot lessons-learned material converges with the customer-integration audit's "process gap" framing: production signing keys need HSM-backed generation with restricted access, and shared dev/partner/test environments must not be assumed lower-security by default [Entrust: secure boot key management lessons learned](https://www.entrust.com/blog/2024/08/mastering-secure-boot-key-management-best-practices-and-insights/). This project's key inventory is not one keypair — it is at minimum UCSK, HPSK, an MCUboot/wolfBoot signing key, and (if a FIPS module is added) a separate module-level key ceremony.
5. **The atomicity gap hiding in "we already have a secure boot chain."** Microchip's own documentation flags that Auto-Update/IAP is not power-loss-atomic at the eNVM-reflash granularity [AC466 application note](https://ww1.microchip.com/downloads/aemDocuments/documents/FPGA/ApplicationNotes/ApplicationNotes/microsemi_polarfire_fpga_auto_update_and_in_application_programming_application_note_ac466_v7.pdf) — exactly the class of bug an A/B-slot bootloader exists to close. Teams that treat "HSS does secure boot, so OTA is solved" will miss that this specific mechanism is the wrong layer for routine field updates.
6. **SNMPv3's own crypto surface.** USM auth/privacy is a second, adjacent cryptographic subsystem distinct from the TLS/wolfCrypt stack; easy to assume "covered" once TLS is in place, but it is not.

### Feeds

- **REQ-HUB-COMMON-002** (no-Linux RTOS/bare-metal control plane) — directly answered: recommend Zephyr.
- **REQ-HUB-COMMON-010** (boot only firmware chaining to platform root; anti-rollback) — HSS's ECDSA P-384/revocation-threshold chain answers the root-of-trust half; the RTOS-image-level anti-rollback half needs MCUboot/wolfBoot's security counter layered on top, which is unproven-on-PolarFire porting work.
