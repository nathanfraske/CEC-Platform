## Survey 5: Redundant CAN + uplinks — honest capability statement

**Scope check.** The Mission-Critical tier-table row (`CEC-Platform-Ground-Truth-Spec.md` §1, tier table: *"Mission Critical | ... | ESP32-P4 plus crypto | Redundant uplinks | Redundant power, CAN, trust"*) is the **only** place either phrase appears; there is no specifying section body anywhere in the spec (confirmed by full-text search — the only other CAN-redundancy-adjacent text is the OQ-31/OQ-60/CAN-FD-deferral material, none of which is about redundancy). Given the LOCKED constraints — one RJ-45 per module, classical CAN 500 kbps on pair 3 only, one shared bus with one fixed 120 Ω split termination at the Hub, TJA1051T/3 transceivers, modules architecturally incapable of a second port — **"redundant CAN" cannot be a module-side or bus-medium property. It can only be a Hub-side property.** This survey treats that as settled going in (per the task framing and `hub-enterprise-requirements.md` §6's own framing, "placement pending D-ENT-6") and researches what's actually buyable within it.

## 1. CAN redundancy — what's actually buyable

### 1.1 Why the classic dual-bus pattern doesn't transfer

Every real redundant-CAN precedent I found is a **duplicated physical medium**, not a Hub-side trick:

- **CANopen Safety (CiA 304)** — the actual standardized CAN redundancy scheme, IEC 61508 SIL-3-capable. Its "Model II" is a fully redundant SCL/DLL/PhL stack: **two independent physical CAN channels**, each carrying one half of a Safety Related Data Object (SRDO) pair (inverted data, different CAN IDs, strict timing window), cross-checked by the receiver [CANopen safety development solutions, can-cia.org](https://www.can-cia.org/fileadmin/cia/documents/proceedings/2017_rupprecht.pdf); [Safety CAN, can-newsletter.org](https://can-newsletter.org/uploads/media/raw/75f5867acda955cd36b66955c87955a0.pdf); [CiA 304 SRDO Add-on, systec-electronic.com](https://www.systec-electronic.com/en/products/cancanopen/add-ons/canopen-cia-304-srdo-add-on). Even CANopen's *single-channel* SRDO variant (two messages, one bus) only detects data corruption on one shared medium — it does nothing for the medium itself failing.
- **ARINC 825** (aerospace CAN) explicitly notes redundancy there means "duplicating critical data across independent network segments" and separately flags that a single CAN bus is a shared multi-master medium whose failure is a communication-wide event unless you add substantial extra hardware to match MIL-STD-1553-class redundancy [tedlinx.com](https://tedlinx.com/arinc-825-can-bus-in-aerospace-bringing-automotive-reliability-to-aviation/); [sitaltech.com](https://sitaltech.com/arinc-825-standard-explained-breaking-down-the-basics/).
- **Automotive dual-bus A/B** (patents, FPGA-based dual-redundant CAN controllers) — same pattern: two full channels (two transceivers, two controllers, two physical nets), switched by a redundancy-management unit on timeout [IJSRP FPGA dual-redundancy paper](https://www.ijsrp.org/research-paper-0514/ijsrp-p2932.pdf).
- **NMEA 2000** "dual backbone" in practice is usually about *power isolation* or *multiple display heads reading the same one bus* (any surviving MFD still sees all sensor data because it's one electrical network), not a duplicated bus in the CANopen-safety sense — one widely-cited marine-electronics piece is literally titled *"A Fundamental Danger of NMEA 2000 Networks"* about the single-bus SPOF risk [morganscloud.com](https://www.morganscloud.com/2013/05/26/nmea-2000missing-the-obvious/); [digitalyacht.net](https://digitalyacht.net/nmea-2000-networking-guide/). I could not find a CiA specification numbered "104" that concerns redundancy — the relevant CiA document for redundancy is 304, not 104; the closest 10x-series hits are connector pin-assignment recommendations (CiA 103/106), unrelated [can-cia.org technical documents](https://www.can-cia.org/cia-groups/technical-documents) [unverified — no CiA 104 redundancy doc located; flag to the requester in case a different number was intended].
- **Fault-tolerant (single-wire-fallback) CAN transceivers exist as a real part class** — NXP TJA1055T, ON Semi AMIS-41682 — and are the closest thing to "buy a transceiver that does redundancy." But they implement ISO 11898-3 **low-speed fault-tolerant CAN, capped at 125 kbps**, and switch a differential pair down to single-wire operation on a wiring fault [onsemi.com AMIS-41682 datasheet](https://www.onsemi.com/download/data-sheet/pdf/amis-41682-d.pdf); [NXP TJA1055T](https://www.nxp.com/products/TJA1055T). This is **incompatible with the platform's LOCKED classical 500 kbps high-speed CAN (ISO 11898-2)** on its own terms — it's not that CEC chose not to use it, it's that the part class doesn't run at the platform's floor speed at all. Reaching for it would mean either violating the 500 kbps floor or bolting on a wire-fault fallback mode the rest of the design (TJA1051T/3, star-with-stubs topology) doesn't support.

**Bottom line: every real "redundant CAN" precedent needs a second physical medium, which the locked one-RJ-45/one-pair module interface forecloses by design, and the one transceiver-class product that promises single-medium fault tolerance runs at a speed the platform doesn't use.** State this plainly rather than reach for a look-alike.

### 1.2 Does a Hub-side dual-transceiver + failover mux even help?

Worth answering precisely, since it's the most plausible-sounding "cheat":

- **What it would cover:** an internal silicon failure of the Hub's own TJA1051T/3 (die failure, ESD latch-up in the driver stage) that takes the Hub off its own bus. A muxed spare transceiver, switched in on fault, restores Hub-side TX/RX.
- **What it would NOT cover — the fault classes that actually dominate real deployments:** a connector fault, a pinched/miswired Cat5e run, EMI, or a stuck-dominant fault from *any module* on the bus. All of these live on the shared `CAN_H`/`CAN_L` net itself, which both transceivers in a mux pair see identically — a digital TXD/RXD mux does nothing about a fault on the wire. Worse: per the locked architecture, **every port's CAN pair joins into one electrical net at the Hub with one fixed 120 Ω split termination** (spec §3.1: "a single TJA1051T/3 sits on one CAN_H/CAN_L net across all ports"). That means most hard-fault types (a short, a stuck-dominant module, a bad crimp pulling the differential out of spec) are **bus-wide events regardless of where they originate** — a fault on module port 6's cable can take down ports 1–8 alike. A Hub-side transceiver mux only defends the narrow slice of faults that originate *inside the Hub's own transceiver silicon* — which, on a mature, ESD-protected, high-volume automotive part like the TJA1051T/3, is also the least statistically likely fault source compared to field wiring/connectors. Spending BOM and adding a mux's own new failure mode (bus contention if both drivers activate, the mux itself as a SPOF) to defend the smallest slice of risk is a poor trade.
- **A cheap, real thing that *would* add value: an independent bus-health witness, not a second communication path.** A low-cost analog tap on `CAN_H`/`CAN_L` (a comparator or spare ADC channel reading bus differential voltage, wired separately from the TJA1051T/3's own RXD) lets firmware distinguish "my transceiver's RX path died" from "the bus itself is faulted" — pure diagnostic value, near-zero cost, and it mirrors a pattern the platform has *already adopted* elsewhere: the §6.13 EPS/PCIe transient-visibility ladder is exactly this move (an INA181-class CSA + comparator riding alongside the primary current-sense chain, purely to *detect and flag*, not to take over the measurement). The same philosophy — cheap, additive, detection-only — is the right model for CAN bus health too, and it's cheap enough to be a nice-to-have rather than a hard requirement.

### 1.3 What IS buyable: fail-detected monitoring

The TJA1051T/3 and the ESP32/TWAI-class controller stack already give most of this **for free, in parts already on the BOM**:

- **TXD dominant time-out (DTO)** is a built-in TJA1051T/3 feature: if `TXD` is held low past `t_TXD-DTO`, the driver disables itself and releases the bus to recessive, self-protecting against a stuck-dominant MCU/firmware fault [NXP TJA1051 datasheet](https://www.nxp.com/docs/en/data-sheet/TJA1051.pdf). This is containment, not reporting — the TJA1051T/3 has no dedicated fault-output pin (its 8th pin is the Silent-mode *input*, not a fault flag), so "detected" has to happen on the MCU/TWAI side, not the transceiver side.
- **TWAI/CAN controller error counters and state machine are already firmware-observable.** Transmit/Receive Error Counters (TEC/REC) and the controller's error-active → error-passive → bus-off state machine are standard, readable via the ESP-IDF TWAI driver's status/alert API on both the ESP32-S3 (Hub Standard/modules) and the PolarFire SoC's hardened CAN peripheral line [ESP-IDF TWAI docs](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/peripherals/twai.html); [CAN bus errors intro, csselectronics.com](https://www.csselectronics.com/pages/can-bus-errors-intro-tutorial). Bus-off triggers at TEC ≥ 256 and is reached in on the order of tens of consecutive errored transmissions — low tens to a couple hundred milliseconds of sustained bus fault at 500 kbps in practice [derived from standard CAN error-counting rules; exact ms figure not directly sourced — unverified]. Recovery, once initiated, needs 128 × 11 recessive bit-times (≈2.8 ms at 500 kbps) before rejoining [csselectronics.com](https://www.csselectronics.com/pages/can-bus-errors-intro-tutorial). **The platform's own firmware roadmap already plans to read this exact primitive for a different purpose** — CLAUDE.md's optional-1 Mbps note: *"Negotiation is Hub-led auto-baud with TWAI error-counter fallback to 500 kbps"* — so recommending TEC/REC monitoring for redundancy alarming isn't a new capability, it's reusing one already on the books.
- **Recovery on the ESP32/TWAI line is software-initiated, not silent-automatic** — bus-off requires an explicit `twai_initiate_recovery()` call, with a state-change callback firing on completion [ESP-IDF TWAI docs](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/peripherals/twai.html); PolarFire SoC's MSS CAN driver exposes an equivalent status/recovery model, per its bare-metal driver source [`mss_can.h`, polarfire-soc/platform](https://github.com/polarfire-soc/platform/blob/main/drivers/mss/mss_can/mss_can.h). That's a feature, not a gap — an automatic silent bus-off recovery loop is exactly what would hide a real fault from the operator; an explicit, logged, alarmable recovery step is what "fail-detected" requires.
- **Self-test without disturbing the live bus**: CAN controllers commonly support an internal/loopback self-test mode (a way to exercise TX→RX and confirm controller+transceiver-digital-path health without transmitting onto the wire) — distinct from Listen-Only/Silent mode (a real mode used for passive bus monitoring/bus-off-safe eavesdropping without ACKing) [CSS Electronics CAN bus intro](https://www.csselectronics.com/pages/can-bus-simple-intro-tutorial); [J1939 Monitor / listen-only mode](https://jcom1939.com/understanding-can-silent-listen-only-mode-and-why-j1939-communication-may-fail/). This is the honest answer for REQ-HUB-COMMON-051's "self-testable... without taking the monitored machine down": self-test the Hub's own transceiver/controller path via internal loopback; do **not** attempt to "test the redundant bus" by injecting traffic onto the live, single, production module bus — there is no spare bus to test in isolation, so a self-test can only ever validate the Hub's own half of the chain, and that scope limit needs to be stated, not implied away.

### 1.4 Recommendation — CAN

**Fail-detected monitoring, not dual-bus, and say so explicitly.** No CAN redundancy scheme found in prior art (CANopen Safety, ARINC 825, automotive dual-bus, NMEA 2000, fault-tolerant transceivers) is deliverable within the locked single-RJ-45/single-pair/single-shared-bus architecture without either violating a LOCKED decision or buying a part class (125 kbps fault-tolerant transceivers) incompatible with the LOCKED 500 kbps floor. What's genuinely buyable, cheaply, and mostly with parts already on the BOM: (1) continuous Hub-side bus-state + error-counter exposure as a monitored/alarmable object; (2) explicit, logged bus-off recovery (never silent); (3) internal-loopback self-test of the Hub's own transceiver/controller path; (4) optionally, a cheap independent bus-voltage witness tap for fault attribution, mirroring the platform's own §6.13 detection-front-end philosophy. This is exactly the audit's "fail-detected redundancy" framing already in `hub-enterprise-requirements.md` §6 — this survey adds the technical grounding for *why* that's the ceiling, not a compromise, and the specific mechanisms to cite when D-ENT-6 closes.

## 2. Redundant uplinks — what's actually buyable

### 2.1 Topology pick: dual native Ethernet, active-standby default

**PolarFire SoC's MSS gives two independent, hardened Gigabit Ethernet MAC instances (GEM_0/GEM_1) for free** — confirmed by the MSS driver source (separate `mpfsxxx_eth1_driver.c` / `mpfsxxx_eth2_driver.c` for MAC0/MAC1) [oryx-embedded.com](https://www.oryx-embedded.com/doc/mpfsxxx__eth2__driver_8c_source.html) and the MSS Configurator User Guide [Microchip, coredocs.s3.amazonaws.com](https://coredocs.s3.amazonaws.com/Libero/12_5_0/pfsoc_mss_ug.pdf). Each MAC has its own independent hardware datapath into the MSS — no fabric logic, no time-division sharing of a single MAC, no soft-MAC design effort. **This is the practical basis for MC's second uplink**: two physically separate Ethernet ports, each with its own PHY (BOM adder — see §4), fed by genuinely independent hardened silicon.

Failover topology, per real-world precedent:
- **Active-standby via link-state detection** is the pragmatic default: sub-second/near-instant detection on carrier loss, configurable poll interval (Linux MII-monitor pattern, hypervisor NIC-teaming "link status" method) [vSphere NIC teaming failure-detection policies](https://vstellar.com/2017/10/vswitch-nic-teaming-and-network-failure-detection-policies/). Crucially, **it requires nothing from the customer's switch** — no LAG/port-channel configuration, no cooperating infrastructure. Given the audit's own named target market (BMC-less ATX-workstation fleets: render farms, trading-desk workstations, industrial PCs — not hyperscale/OCP switch fabrics), that switch-agnostic property matters more than raw failover speed.
- **802.3ad/LACP active-active** is a legitimate opt-in enhancement — official failover figures run **as low as 250 ms, with a spec maximum around 2 s**, faster with `lacp_rate=fast` (1 s LACPDU interval vs. the 30 s default) [Mikrotik/RouterOS LACP bonding study, arXiv](https://arxiv.org/pdf/2108.02935); [Link Aggregation and LACP basics, Thomas-Krenn](https://www.thomas-krenn.com/en/wiki/Link_Aggregation_and_LACP_basics) — but it needs a LAG configured on the attached switch, which not every customer network offers or permits on an unmanaged/appliance-class port. Recommend it as an **operator-selectable mode**, not the default.
- **IEC 62439-3 PRP/HSR** (zero-loss dual-LAN packet duplication, the substation-grade gold standard) was researched and is explicitly **not recommended**: PRP requires the customer's network to be doubled end-to-end (two independent parallel LANs) via PRP-aware "RedBox" silicon or software duplication logic [scadaprotocols.com PRP vs HSR guide](https://scadaprotocols.com/prp-vs-hsr-iec-62439-3/); [TTTech HSR/PRP for smart grid networks](https://www.tttech.com/know-how/hsr-prp-smart-grid-networks). Neither PolarFire's hardened MSS nor its fabric includes PRP/HSR IP out of the box — building it would be a fabric-cost item (LUTs + real design effort), and it assumes exactly the kind of doubled substation/grid-class network infrastructure the platform's own named target market (BMC-less ATX-workstation fleets) is unlikely to run. Right technology, wrong customer.

### 2.2 Ethernet + USB — heterogeneous, not equivalent

USB is a legitimate **third, diverse-media** channel, but it is **not a valid redundant peer to the Ethernet pair for the specific "loss of redundancy" alarm this register is drafting**, and conflating the two would misstate coverage:

- USB's functional path requires the **host OS and a running agent process** to relay anything further — even though the Hub itself is 5VSB-powered and host-independent (spec §2.9), the USB link is only useful once something on the host is alive to read it. This is precisely the audit's own finding #5 (*"USB-primary... telemetry that dies with the host"*) and precisely why `REQ-HUB-COMMON-025` treats "host-down operation" as a verified test case exercised over the **network** path, not USB.
- Ethernet has the opposite property by design: it's the Hub-driven, host-independent path.
- **The two paths therefore cover disjoint fault domains**: dual-Ethernet covers "network/switch/cable/PHY failure while the host may or may not be up"; USB covers "local sensing/provisioning/debug while the host is up" but contributes *zero* coverage to the platform's flagship host-down guarantee. A "redundant uplink" claim that quietly counts USB as the second leg would be *less* honest than the CAN single-path admission this same register already makes for the sensing chain (`REQ-HUB-COMMON-053`) — it deserves the same explicit treatment, not a pass.
- Prior art for this exact heterogeneous-but-unequal pattern exists in BMC/OOB management: dedicated-vs-shared-NIC failover plus serial-console fallback is standard practice, but nobody markets the serial console as "redundant to the network path" in the fault-tolerance sense — it's a documented, different-purpose backup channel [Out-of-band management, Wikipedia](https://en.wikipedia.org/wiki/Out-of-band_management); [OOB Management & BMC, ai-infrastructure.net](https://ai-infrastructure.net/oob-management-bmc/).

### 2.3 ENT-AIR: "dual" means dual *local* paths, not dual network egress

The task asks directly: "ENT-AIR dual = what?" Working through it against the platform's own documents:

- `REQ-HUB-AIR-024` already commits ENT-AIR to **zero network egress by design**. A second network uplink is a category error there — there's no "primary uplink" to be redundant *to*.
- What legitimately survives as "redundant" on ENT-AIR is **redundant local operator paths**: e.g., USB plus a physical console/serial interface, or USB plus removable-media export, matching the "operator port / console / removable export" language `REQ-HUB-AIR-024` already uses. Two independent local channels for extraction/alerting, neither touching a network.
- **A real, unresolved tension worth flagging explicitly, not waving through**: spec §2.9's forensic-recovery path has the NanoKVM egress persisted Hub data **over its own Ethernet or WiFi** when a wall-wart powers a dead system (*"the NanoKVM egresses it over its own Ethernet or WiFi, so the data comes out without opening the case"*). If that NanoKVM link is present and enabled by default on an ENT-AIR build, it **is** a second network path, silently contradicting "zero network egress by design." This needs to be either (a) a documented, policy-gated, disabled-by-default exception invoked only during an explicit dead-system-recovery procedure, or (b) removed/fused off on ENT-AIR builds entirely — but it cannot be left as an unexamined default. This directly compounds the already-open ENT-AIR radio-posture question (D-ENT-5, plan §1a.5) since NanoKVM WiFi is itself an RF emitter.

### 2.4 Recommendation — uplinks

**MC tier**: two independent Ethernet ports off PolarFire's two hardened GEMs (default: link-state active-standby, switch-agnostic; operator-selectable LACP active-active where the customer's switch supports it); USB retained as a third, explicitly-scoped local/enrichment channel, documented as *not* counting toward the network "loss of redundancy" alarm; PRP/HSR researched and declined as a requirement (right standard, wrong served market). **ENT-AIR**: "redundant uplink" reframed as redundant *local* operator paths; the NanoKVM's own network/WiFi forensic-egress path is flagged as a live tension against the zero-egress claim and needs an explicit adopt/gate/remove decision, not a silent pass.

## 3. Failover semantics + alarm requirements ops teams expect

| Mechanism | Raw fault-detection time | Source |
|---|---|---|
| Ethernet link-state loss (carrier sense) | Sub-second, poll-interval-bound (MII-monitor pattern) | [vSphere teaming policies](https://vstellar.com/2017/10/vswitch-nic-teaming-and-network-failure-detection-policies/) |
| LACP link failover | ~250 ms typical, ~2 s spec max (faster with `lacp_rate=fast`) | [arXiv Mikrotik LACP study](https://arxiv.org/pdf/2108.02935); [Thomas-Krenn LACP basics](https://www.thomas-krenn.com/en/wiki/Link_Aggregation_and_LACP_basics) |
| CAN bus-off entry (sustained bus fault, 500 kbps) | Low tens–low hundreds of ms [unverified, derived] | Standard CAN error-counting rules; [CSS Electronics CAN errors](https://www.csselectronics.com/pages/can-bus-errors-intro-tutorial) |
| CAN bus-off recovery (once initiated) | ≈2.8 ms (128×11 recessive bits @ 500 kbps) | [CSS Electronics](https://www.csselectronics.com/pages/can-bus-errors-intro-tutorial) |
| Telecom 1+1 APS (reference ceiling, not a CEC target) | Switch-to-protect ≤10 ms, error-free path ≤50 ms (SONET/ITU G.8031 class) | [Analog Devices, hitless 1+1 protection switching](https://www.analog.com/en/resources/technical-articles/hitless-protection-switching-with-11-redundancy.html) |

**Takeaway for the register:** the underlying fault physics (link-state, LACP, CAN error-confinement) all resolve in well under one second. The `hub-enterprise-requirements.md` §6 draft's existing bound — *loss alarmed ≤1–5 s* (from `research/customer-integration-audit-2026-07-01.md` §5's MC candidates) — is therefore **not physics-limited, it's alerting-pipeline-limited** (debounce, the northbound trap/API path, the AIR local-surface path), and is comfortably achievable; if anything it's conservative headroom, not a stretch target. Two things worth adding to the requirement text itself:

- **Debounce/hold-off is a named requirement, not an implementation detail.** Telecom APS practice explicitly builds in alarm hold-off to prevent nuisance switching on transient blips [Analog Devices 1+1 protection](https://www.analog.com/en/resources/technical-articles/hitless-protection-switching-with-11-redundancy.html); a naive "alarm the instant TEC ticks up" implementation would flap on ordinary bus noise. The register should require a defined debounce window, not just a bound.
- **The alarm object should map onto the Redfish `Redundancy` resource** (`Mode`, `MaxNumSupported`, `MinNumNeeded`, `RedundancySet`, `Status`) already used for `PowerSupply`/`NetworkAdapter` redundancy on enterprise gear [DSP2046 Redfish Resource and Schema Guide](http://redfish.dmtf.org/schemas/DSP2046_2020.4.html) — this is the schema `REQ-HUB-NET-020`'s Redfish exposure would need to plug into for the CAN/uplink redundancy elements, and it's a real, already-standardized target rather than a bespoke CEC object.
- **Self-test is scope-limited, and the limit should be stated.** For CAN there is no spare bus to test against (§1.3); for the Ethernet pair, a genuine self-test *can* pull one link (or simulate LACP partner loss) and confirm failover completes within the bound, since a real second physical path exists there — unlike CAN, this one is fully testable end-to-end.

## 4. What PolarFire's dual MAC/fabric gives for free — and what it doesn't

**Free (already in hardened MSS silicon, no fabric cost, no extra design effort):**
- Two independent Gigabit Ethernet MAC instances (GEM_0/GEM_1) [oryx-embedded.com driver source](https://www.oryx-embedded.com/doc/mpfsxxx__eth2__driver_8c_source.html); [MSS Configurator UG](https://coredocs.s3.amazonaws.com/Libero/12_5_0/pfsoc_mss_ug.pdf).
- Two independent hardened CAN controller instances (CAN0/CAN1), evidenced by distinct memory-mapped register blocks and a driver that addresses them separately [`mss_can.h`, polarfire-soc/platform](https://github.com/polarfire-soc/platform/blob/main/drivers/mss/mss_can/mss_can.h). Whether the hardened block is classical-only or CAN-FD-capable was not confirmed from available excerpts of the MSS Technical Reference Manual [unverified — confirm CAN0/CAN1 FD support directly against the MSS TRM CAN chapter before costing].

**What "free" does NOT mean here — the two gotchas to carry into D-ENT-3 costing and D-ENT-6:**
1. **A second Ethernet MAC still needs a second PHY, magnetics, and connector** — real BOM line items, not silicon-included. "Free" means no fabric-LUT cost and no soft-MAC development risk, not a free port.
2. **The second hardened CAN controller cannot be pointed at the module-facing bus to get redundancy there** — the module link's pin allocation gives exactly one CAN pair (pins 3/6) per RJ-45, and the Hub's own architecture sums every port onto one shared `CAN_H`/`CAN_L` net with one termination. A second on-die CAN controller has nowhere LOCKED to attach a second physical module bus without violating the pin table. Its only honest uses here are Hub-internal (e.g., a board-to-board/mezzanine link, or the kind of Hub-side diagnostic loopback in §1.3) — not "redundant module sensing."
3. Fabric could, at real design cost, add things the hardened MSS doesn't include for free — a soft PRP/HSR RedBox, a soft TSN switch, a third/fourth soft MAC — but none of that is warranted for this survey's recommendation (§2.1), so it's noted as available headroom, not proposed.

## 6. Prior-art comparison table

| System / standard | Redundancy model | Physical requirement | Transfers to CEC? |
|---|---|---|---|
| CANopen Safety (CiA 304) | Dual physical channel (Model II) or dual-message-one-bus (SRDO) | 2nd CAN medium, or accepts single-medium risk | No — no 2nd medium available; SRDO-style dual-message-on-one-bus is a data-integrity check, not a medium fault fix |
| ARINC 825 (aerospace CAN) | Duplicated independent network segments | 2nd CAN medium | No, same reason; also explicitly flags single-bus CAN as SPOF-prone without major extra hardware |
| Automotive dual-bus A/B | 2 full channels + redundancy-management unit | 2nd CAN medium, 2nd controller | No |
| ISO 11898-3 fault-tolerant transceivers (TJA1055T, AMIS-41682) | Single-medium fallback to single-wire mode | Compatible transceiver + wiring | No — capped at 125 kbps, below the platform's LOCKED 500 kbps floor |
| NMEA 2000 "dual backbone" | Multiple nodes reading one shared bus | 1 medium | Not real bus redundancy; informative as a cautionary example, not a pattern to copy |
| IEC 62439-3 PRP/HSR | Zero-loss dual-LAN packet duplication | 2 parallel Ethernet LANs + PRP-aware silicon | No — substation-class, wrong served market, no hardened PolarFire IP |
| 802.3ad LACP | Active-active link aggregation | Cooperating switch (LAG) | Yes, as an opt-in enhancement over 2 native PolarFire GEMs |
| Link-state active-standby | Simplex failover on carrier loss | None beyond 2 NICs | Yes — the recommended default for the uplink pair |
| BMC dedicated/shared NIC + serial fallback | Heterogeneous, unequal-coverage paths | 2nd NIC or serial/console | Yes — models the Ethernet+USB relationship honestly (diverse, not equivalent) |

**Summary for the caller:** No form of real "redundant CAN" survives the locked single-RJ-45/single-pair/single-shared-bus module interface — every industrial/automotive/aerospace precedent needs a second physical medium, and the one transceiver class that promises single-medium fault tolerance (ISO 11898-3, 125 kbps) is incompatible with the platform's locked 500 kbps floor. The honest, buyable answer is Hub-side fail-detected monitoring (bus state + error counters + alarm + scoped self-test), using capability the TJA1051T/3 and TWAI-class controllers already have. For uplinks, PolarFire's two hardened Gigabit Ethernet MACs give a real, silicon-free basis for a genuine dual-port MC uplink (active-standby default, LACP opt-in) — but USB is not a valid redundant peer to it (host-dependent, doesn't cover the platform's own host-down guarantee), and on ENT-AIR "redundant uplink" has to be reframed as redundant local paths, with the NanoKVM's own network/WiFi forensic-egress path flagged as an unresolved tension against "zero network egress by design." Six register-ready REQ candidates and the D-ENT-6/Phase-4 language fix are drafted above.
