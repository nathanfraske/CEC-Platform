## Survey 3: RJ-11 trust channel — recommendation

**Recommendation: DEFINE-AS a narrow, single Hub-resident physical-security I/O port — a supervised tamper-loop input paired with a Hub-driven dry-contact alarm output — and rename it off "trust channel."** Identity/attestation duty is better served by silicon already on the roadmap (PolarFire PUF + IDevID, REQ‑HUB‑COMMON‑001/003) and by OQ‑60's own proposal to move "trust and attestation" onto a second CAN‑FD channel + the secure element. A 6‑conductor phone‑style jack was never going to out‑trust a hardware root of trust; it can, however, do something CEC has nothing else for: carry a facility‑visible, network‑free, always‑on physical‑security signal in and out of the Hub. This is speculative in the sense that it is a new proposal, not an existing repo decision — but it is the only candidate that survives a redundancy check against what's already locked (see comparison table).

**Runner-up: a local physical‑presence/consent loop gating Appendix‑D Stage‑5 plan actuation.** This is a real, currently‑unfilled gap — Stage 5's preconditions (D.2, D.6) are a judge signature, rendered consent, and a verified restore point, all software; nothing today requires a human to be *physically at the machine* before a signed remediation plan executes. But it's a weaker case for a *dedicated external connector*: the property it needs (proof a human is locally present) is normally satisfied by an on-board button (the Hub already has one — the GPIO0 hidden service button) unless CEC specifically wants consent authority separable from whoever can open the case. I rank it second because that separation argument is plausible but unstated in any requirement today, whereas the alarm‑I/O case is already implied by three separate requirements (070/071/072, see below).

**The honest drop case.** Two things cut against populating this connector at all right now. First, the strongest surviving function (tamper‑loop sensing) is *also* buildable as an ordinary module — CEC's whole architecture is "hang a sensor off an RJ‑45 port over CAN," and a chassis‑intrusion module doing exactly that is already candidate #1 in the tamper‑module roadmap. A dedicated Hub connector only earns its place for the **output** half (driving a facility alarm from the Hub's own always‑on §2.9 domain, which must work even with the monitored PC fully dead) — the input half doesn't obviously need one. Second, the consuming feature (chassis‑intrusion + tamper log) is itself an *unratified* Phase‑3a candidate, not an adopted module family; specifying hardware for a function whose consumer doesn't exist yet risks committing the exact "shipped it because we felt we should" mistake REQ‑HUB‑COMMON‑033 exists to prevent, just one level removed (an unpopulated, unexplained-to-a-security-auditor jack is itself a finding in a procurement review). My practical resync of these two pulls: **write the concrete definition now** (satisfies REQ‑HUB‑COMMON‑033's letter — it is no longer an unspecified connector) **but gate physical population of the footprint on the tamper‑module‑roadmap concept‑1 adopt decision at Phase 3**, not before. If the owner declines concept 1 *and* declines the Stage‑5 physical‑presence idea, the honest call is to drop the connector outright and let the NanoKVM aux link + USB (already locked, see below) absorb whatever residual local‑I/O need remains.

**A live collision to flag, not paper over.** OQ‑60 (spec, PROPOSED) already reaches for this exact connector shape — "the per-port companion connector planned for the Enterprise out-of-band trust channel, an RJ-11 6P6C alongside each RJ-45" — and proposes repurposing it, **one per module port, on any Hub tier that services a Max module** (not Enterprise-only), as a 12VHPWR Max power + bidirectional FREEZE-trigger sideband, explicitly stripping "trust and attestation" off it onto CAN‑FD + the secure element but keeping an "external‑dongle and physical‑override" fragment. That is a different cardinality (N‑per‑Hub, platform‑wide) and a different owning decision (OQ‑60, gated separately) than my Enterprise‑scoped, one‑per‑Hub security‑I/O answer. Both proposals want the same 6P6C shell; they cannot both win the name "the RJ‑11" without the requirement being rewritten. **D‑ENT‑5 and OQ‑60 need to be resolved as one decision, not two independent ones**, or CEC ends up with two incompatible specifications for the same connector footprint.

### Proposed pinout + isolation — recommended function (physical-security I/O)

6P6C jack, contacts numbered 1–6 left to right (clip down, contacts facing you — same convention CEC already uses for the RJ‑45 table):

| Pin | Signal | Notes |
|---|---|---|
| 1 | `ALARM_OUT_NO` | Hub-driven isolated output (opto-MOSFET or small reed relay), normally-open dry contact toward the facility panel |
| 2 | `ALARM_OUT_COM` | Return/common for the alarm relay |
| 3 | `LOOP_IN_A` | Supervised sense input — external loop terminated in an end-of-line resistor, so open **and** short both read as distinct non-normal states |
| 4 | `LOOP_IN_B` | Return for the supervised loop |
| 5 | `AUX_ISO_5V` | Optional current-limited, reverse-isolated supply for a passive external switch/LED (same Schottky+current-limit pattern already used at §2.7/§2.9 for untrusted external power) |
| 6 | `ISO_GND` | Isolated return for pin 5 — kept off board GND until the far side of the opto/relay boundary |

Isolation notes:
- **Galvanic isolation is not optional here** — unlike every other CEC connector, this one is designed to leave the enclosure/rack toward a facility panel that may sit on a different earth reference, with a longer run and real surge exposure. That is the *opposite* of §2.4's rationale for dropping PoE‑grade protection on the module RJ‑45 ("an internal interface... not exposed to the commodity‑cable cross‑connect threat") — here the threat model is explicitly external, so this port arguably deserves **stronger** transient/surge protection than the internal‑grade PESD5V0S1BA used on DETECT, not a straight reuse. Flagging this as an open sizing question rather than assuming the existing part is adequate.
- Loop supervision (EOL resistor) directly answers the tamper‑module‑roadmap's own critique of the OEM baseline: a plain switch "only logs a binary open/closed state" and is defeated by simply cutting the wire; EOL supervision makes cut-and-short both alarmable.
- Every event on this port should write into the *same* rollback-resistant tamper log (REQ-HUB-COMMON-070) and ride the persist-on-fault path (REQ-HUB-COMMON-062/071) — not a parallel logging mechanism.
- Deliberately **no data protocol, no parser, no path to CAN/DETECT** — this is the load-bearing property, not a limitation (see threat model).

*Runner-up sketch (consent-loop), lighter treatment:* 2 pins minimum (momentary NC/NO contact from an external keyswitch or bezel button), isolated the same way, feeding a new Stage‑5 precondition ("physical presence confirmed within N seconds of consent render") in Appendix D §D.6. Could technically share the same 6P6C shell as two more conductors if both functions were ever adopted together, but I'd treat that as scope creep on a single low-pin jack rather than recommend it — better to ship one narrow function than one overloaded one, echoing the caution already implicit in OQ‑60 about not stacking too many roles onto this shell.

### Threat model

An attacker who reaches the security-I/O cable run — which, by design, may leave the rack toward a facility panel and is therefore more exposed than any other CEC connector — can attempt to: cut or short `LOOP_IN` to silence a tamper alarm, defeated by EOL-resistor supervision, which turns both failure modes into distinct alarm states instead of silence; drive `ALARM_OUT` from the field side to force a false trigger or false-suppress, bounded by the output being Hub-sourced through a low-impedance relay/opto stage and by the Hub's own tamper log recording the state change regardless of what happens to the signal downstream; or back-feed/fault `AUX_ISO_5V`, bounded by the same reverse-isolation-Schottky-plus-current-limit pattern already used on every other external power input in §2.7/§2.9. What the attacker categorically **cannot** do is reach telemetry, control, or the Appendix-D actuation chain through this port — it carries no protocol and no parser, so unlike a UART/console candidate it needs none of the "untrusted input, bounded parser, no privileged Hub control reachable" hardening OQ-52 had to write for the NanoKVM link. That is deliberate: it applies the same "auditable and boring" posture Appendix D's agent-neutrality rule (D.3) mandates for the on-machine software agent, to a piece of hardware instead — the worst a field attacker can do is flip one alarm bit, not talk to the platform.

### Variant conditionality

- **ENT-AIR: populate by default.** Air-gapped builds have no syslog/SIEM path (REQ-HUB-NET-021 is NET-only) but are explicitly obligated to "surface the same events on the local operational surface" (REQ-HUB-NET-072). A dry-contact output needs no network stack at all to satisfy that — arguably the canonical zero-network answer for a physical-security event, and it matches the facility-security-conscious buyer profile the tamper-module-roadmap research assumes.
- **ENT-NET: optional/companion, populate-on-request.** REQ-HUB-NET-021 already gives NET a syslog/SIEM path for tamper events, so the dry contact becomes a secondary integration point for older BMS/fire-panel infrastructure that predates SIEM (common in regulated facilities) rather than load-bearing. Leaving the footprint unpopulated by default on NET (vs. populated on AIR) is exactly the kind of visually-inspectable variant divergence REQ-HUB-AIR-101 already asks for.
- **MC / redundancy tie-in (contingent on D-ENT-6):** if Mission Critical ends up owning the redundancy set (REQ-HUB-COMMON-050/052), the same alarm circuit is a natural, low-cost carrier for a "redundancy degraded" event alongside "tamper" — noted as a possible unification, not a requirement.

One correction to the spec's own framing, worth carrying back: OQ‑60 states the RJ‑11 "cannot mismate an RJ‑45 jack." That's only true in the direction that matters — an 8P8C plug is physically too wide to enter a 6P6C jack, so no CEC module/NanoKVM cable can ever land on this port. The reverse is not fully blocked: a 6P6C plug can partially insert into an 8P8C jack (RJ‑45/RJ‑12 share a 1.02 mm contact pitch), touching only the jack's center contacts, making no functional connection but risking bent/deformed contacts on repeated insertion. For CEC this means the dangerous direction (protecting the security port and its CAN/5VSB-adjacent logic from a stray module cable) is fully solved by connector geometry alone, but the minor direction (someone absent-mindedly jamming the security cable into a spare module port) is a labeling/panel-layout problem, not a solved one — worth a distinct silkscreen/color callout on the security jack, the same way Cisco shipped a visually distinct light-blue rollover cable even though its console port used the same 8P8C shell as its Ethernet ports.
